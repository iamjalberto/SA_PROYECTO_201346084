Terraform – Validación en CI/CD

terraform-validate:
  steps:
    - terraform fmt -check -recursive   # [1] estilo
    - terraform init -backend=false     # [2] módulos
    - terraform validate                # [3] sintaxis HCL
    - terraform plan -out=tfplan        # [4] plan sin apply
    → artifact: tfplan (7 días)

Bloquea build-and-push y deploy si falla.

CronJob – Rechazo Automático de Órdenes

Problema: Órdenes en estado CREADA abandonadas bloquean la vista del restaurante.


Solución: CronJob cada 5 minutos.

  • Busca órdenes CREADA > 60 min
  • Cambia estado → RECHAZADA
  • Notifica via RabbitMQ order.rejected
  • Anti-spam: tabla order_notifications
  • Log: Rechazadas/Notificadas/Omitidas
spec:
  schedule: "*/5 * * * *"
  concurrencyPolicy: Forbid
  activeDeadlineSeconds: 240
  successfulJobsLimit: 3
  failedJobsLimit: 1

# Output ejemplo:
# [OK]  Rechazadas: 3
# [MSG] Notificadas: 3
# [IGN] Omitidas (anti-spam): 0

Conclusiones

Infraestructura como Codigo
  • Terraform elimina la configuracion manual y hace el entorno reproducible
  • Ansible orquesta la VM de load-testing sin intervención humana
  • Toda la IaC vive en el repo y pasa por CI antes de aplicarse
Observabilidad
  • ELK centraliza logs de todos los servicios en un solo índice
  • Prometheus + Grafana exponen métricas de latencia, errores y recursos
  • Las alertas permiten reaccionar antes de que el usuario lo note
Automatizacion y Calidad
  • El CronJob de rechazo protege la consistencia del negocio sin código nuevo
  • Locust demostró que el sistema soporta 20 usuarios concurrentes
  • Smoke tests en CI garantizan que cada merge no rompe los contratos
Lecciones Aprendidas
  • Separar plan de apply en CI evita cambios accidentales en producción
  • Sin logs estructurados, buscar un error toma horas; con ELK, segundos
  • SCRUM + DoD definido impidió entregar tareas "casi listas"
